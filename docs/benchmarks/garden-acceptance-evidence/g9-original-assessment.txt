# Completed Garden acceptance and release qualification

**Assessment: HOLD.** Durable-write latency, bounded lexical recall and contention
availability fail accepted workload gates. The 100k run was terminated by its
resource guard during the final audit; 1m stress exceeded its load deadline and native
AnimaOS service interoperability fails descriptor admission. This report covers the
completed native engine and additive sharing boundaries, separately from the
earlier [G2 experiment](2026-11-14-garden-engine.md). No binary installation,
published release, tag, live migration or live harness setting change is part of
this assessment.

G8 was revalidated, committed and pushed to `origin/main` at
`df6c6eb07337ab28a153f5c9decf27d63b34d8d1` before G9 work began. The G9 source is
in the isolated `g9000/mother-garden-release` branch. AnimaOS acceptance uses the
separate `g9000/mother-additive` worktree; that implementation is not present in
AnimaOS main. Unrelated web UI changes in its primary checkout are preserved.

## Release boundaries

Release A adds selected sharing and additive recall without replacing native
harness memory. Release B/C supplies extensible temporal graph storage, native
v1 compatibility, full backups and the explicitly selected SQLite-free runtime.
These are separate acceptance claims. The default build retains SQLite runtime
and conversion support; `--no-default-features` builds the native executable.

Harnesses extract, select, summarize, interpret and rank. Mother stores attributed
canonical records, temporal evidence and revisions, enforces current grants,
provides bounded candidate queries and commits owner-reviewed proposals. Pending
proposals are not canonical recall; owner approval does not itself prove vector
index preparation or actual host/model recall. Persona adoption is optional and
independent of sharing.

## Completed-engine measurement method

`examples/garden_acceptance.rs` accepts only explicit synthetic generation and
owns its temporary database. It seeds through actual authenticated public
`GardenStore` v2 operations in at most 64-item batches, with canonical receipts,
history and all production indexes. Durability and access checks remain enabled.
This differs materially from G2's compact integer-key experimental schema and
256-entity bulk chunks; G2 results are not copied as completed-engine results.

The measured runner source SHA-256 is
`B75BDF704B4C44C92B2A0816FFC52FE532900A825D0FCFB8E5540183C0AE857E`.
Its engine/runner were built before the installer-only dependency isolation.
The runner source and measured engine remain unchanged, but these measurements
are not from the same final Cargo artifact as the post-isolation qualification
builds. Final source/build manifests must retain that distinction.

The logical graph uses G2 seed-14 endpoint mixing and sampling, five assertions
per entity and a distinct canonical evidence source. Requested datasets are
10,000/50,000, 100,000/500,000 and a separate 1,000,000/5,000,000 stress case.
UTC temporal intervals, engine-generated UUIDs and full evidence/history adapt
that topology to the public v2 contract.

Measurements include warm and application-cache-reopened exact reads, bounded
temporal/neighborhood and lexical queries, 32-assertion Immediate batches,
four-reader/two-writer contention, explicit high-degree and history-heavy
queries, final canonical/index audit, database bytes and externally observed
process memory/disk growth. There is no OS/drive cache flush; reopened reads are
not cold-disk measurements. Public query responses do not expose examined-work,
visited-node or writer-acquisition counters, so those remain unavailable rather
than inferred from requested budgets.

Percentiles use nearest-rank samples. The original provisional warm p95 budgets
remain exact lookup 10 ms, bounded query 50 ms, durable 32-assertion batch 100 ms
and lexical candidates 100 ms. Failed requests retain separate raw latencies and
error counts; they never satisfy a successful latency budget. The optimistic
current-authority fence can return `RestartRequired` if a canonical write races
a query. No benchmark request is automatically retried.

Process exit zero means execution completed. Acceptance uses the JSON
`workload_gates_pass`, `latency_budgets_pass`, `semantic_gates_pass` and
`availability_pass` fields.
Progress files are last checkpoints; after forced termination they may lag
committed state and are not proof of no later writes. Final reports aggregate
all workers' acknowledged writes and audit those counts. Deadlines are checked
between public calls; an external process guard retains interrupted synthetic
state instead of cancelling inside a transaction or retrying an uncertain write.

Both runs loaded 10,000 entities, 50,000 initial assertions and one evidence

latency remains a separate unmeasured cost.

Windows initial load took 275.05 s and the full run 363.31 s. Linux initial load
took 78.77 s and the full run 119.68 s. The final database was 1,140,854,784 bytes
in both runs. Externally observed peak working set/RSS was 3,941,769,216 bytes

engine work budget or query policy to improve a score.

## Separate 1m stress

The 1,000,000-entity/5,000,000-assertion invocation exited with code 1 and
`soft_deadline_exceeded` after 3,600.411 s, still in `seed_entities`. Its
[final execution report](garden-acceptance-evidence/linux-1m.json) records
802,752 acknowledged entities, zero assertions/history updates and 12,544
receipts. It has `completed: false`, `workload_gates_pass: false` and no timed
query/write metrics. Relationship loading, later workloads and the final audit
were never reached. These are caller-reported acknowledgements, not audited
canonical counts or a completed million-entity graph.

The [resource observations](garden-acceptance-evidence/linux-1m-resources.json)
record 1,255,124,992 bytes peak process RSS and a 15,167,623,168-byte database
across 7,008 samples. Neither RAM/disk guard nor external forced termination
fired; the runner stopped cooperatively between calls at its unchanged one-hour
deadline. This is a failed completion-budget gate, not an out-of-memory result
or proof that the store cannot eventually hold the requested corpus. No 1m
capacity, query latency, full graph durability or audit pass is claimed.

Failed-run synthetic databases and original logs remain in task-owned private
directories outside Git for profiling. Git contains only source and synthetic
measurement summaries; disposable AnimaOS test temporary files were removed.

## Reproduction commands and evidence scope

Run Mother checks from its isolated release source, with `CARGO_TARGET_DIR` and
temporary directories set to separately owned qualification paths. Windows and
Linux use the same Cargo command forms; their compiler/platform results remain
separate. Documentation checks set `RUSTDOCFLAGS=-D warnings`:

```text
cargo fmt --all -- --check
cargo test --locked
cargo build --release --locked
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo doc --locked --no-deps
cargo test --locked --no-default-features
cargo build --release --locked --no-default-features
cargo clippy --locked --no-default-features --all-targets -- -D warnings
cargo doc --locked --no-default-features --no-deps
cargo tree --locked --no-default-features --edges normal,build
cargo check --locked --no-default-features --all-targets --target x86_64-apple-darwin
```

The dependency tree audit inspects normal/build edges rather than inferring
runtime inclusion from the entire lockfile. Native installer refusal is covered
by the ordinary native suite and can be selected with
`cargo test --locked --no-default-features --test native_model_boundary`.
The macOS command is a compile check only. Windows tests/builds/lints/docs ran
in a dedicated qualification target directory. Source/build hashes are retained
separately from measurements; no zero-test filter is counted as acceptance.

The benchmark was built and invoked with these exact command forms; all other
runner parameters use their checked-in defaults:

```text
cargo build --release --locked --no-default-features --example garden_acceptance
<built-example-path>/garden_acceptance --synthetic --entities 10000 --deadline-seconds 3600 --keep-database
<built-example-path>/garden_acceptance --synthetic --entities 100000 --deadline-seconds 3600 --keep-database
<built-example-path>/garden_acceptance --synthetic --entities 1000000 --deadline-seconds 3600 --keep-database
```

On Windows the executable has the `.exe` suffix. The task-owned monitoring
wrapper is not a committed runner: it samples every 500 ms and guards RSS above
12,582,912 KiB (12 GiB), host `/mnt/c` free space below 20,971,520 KiB (20 GiB)
or external elapsed time above 3,720 s. The runner's cooperative 3,600 s deadline
is checked between API calls and cannot interrupt an active transaction/audit.
No committed wrapper or cancellation guarantee is implied.

Run AnimaOS checks from the separate additive worktree through its managed Rust
wrapper, preserving the workspace's target/cache policy. On Windows set
`TEMP`/`TMP` to a short, owner-private synthetic directory for the full run:

## Operational recovery and remaining release gates

Source review suggests the next performance work in this order. These are
implementation hypotheses, not controlled explanations of the measurements:

1. Bound the [canonical/index audit](../../src/garden/indexes.rs). It currently
   retains full record/history/index collections and scans sequence keys for
   each receipt. Streaming comparisons and grouping by sequence must retain
   exact missing, extra and corrupt-entry detection before scale tests repeat.
2. Improve lexical candidate selectivity. The first-trigram index chooses the
   same prefix for these fixture names, then exhausts its work budget before
   full matching. Investigate selective-gram intersection or an exact-name
   path, preserving short-substring behavior, canonical validation and coverage.
3. Profile durable writes by writer wait, preparation, index work and commit
   time before changing the transaction path. Keep Immediate durability and
   atomic receipts; cross-platform timings do not establish filesystem causality.
4. Investigate snapshot timing around clock-write admission under contention.
   Retain fresh authorization, genuine clock-rollback detection and the final
   current-authority fence. Do not hide rejection rates with automatic retries.

Follow the [local service](../garden-service.md),
[full backup](../garden-backups.md) and
[migration/rollback](../garden-migration.md) guides. Stop the native owner before
direct database administration. Runtime upgrades preserve identity/generation;
restore and explicit migration change generation. Reissue exact restrictions to
new private files, and never remove fences or reset operation UUIDs to recover
an uncertain outcome. A rollback after canonical destination changes requires
verified reconciliation and cannot discard acknowledged writes.

Physical power loss, actual hosted model selection/recall, visual browser/TUI
acceptance and installed harness adoption are not established by these synthetic
checks. An owner must review the concrete report before live migration or
installation. Pending, failed and unavailable gates keep the release assessment
at HOLD.
