# Propose a letter for owner review

Continue only after the owner asks to submit the specific draft or correction. A request to write, revise, keep a draft private, or illustrate it leaves the inbox and canonical records untouched.

If a source was authorized for the private draft only, omit that source and the material it supports, redraft from sources authorized for review, or clarify permission before submitting. When the owner already authorized the exact draft and review destination, proceed without asking again.

1. Use the configured M.O.T.H.E.R v1 connection. Read current workspace ID and restore generation from mother_get_capabilities (workspace.workspaceId and workspace.generation) or an authorized mother_get_context response (workspace.id and workspace.generation). Preserve the owner's selected recall profile if using context.
2. For a new entry, set expectedRevision to 0 and omit the top-level id. For a correction, search for the entry if necessary, then resolve the complete current canonical memory with mother_get_record. Verify its identity, period, writer, and revision against the draft being corrected. If the current entry differs from the version the owner chose, ask the owner to reconcile the difference before submitting.
3. Keep the original entry date, period and writer visible in the correction. Credit the person or agent who prepared the correction separately and date the change. Preserve source IDs, cited revisions, and existing HTTPS source links, including older evidence as historical provenance where it no longer supports the corrected reading. Distinguish superseded evidence from current evidence. Retain the existing record's references and sources, adding verified new references. If you cannot verify enough of the existing entry or source chain to preserve it, ask for the missing evidence before proposing a replacement. Refer to a prior letter revision by the same record ID and revision in the prose rather than using a self-reference in the record's references array.
4. Call mother_propose_memory once with a fresh operationId UUID, workspaceId, generation, expectedRevision, a concise source attribution, and basis set to model_inference. For a correction include the existing record's top-level id and use its current revision as expectedRevision. The record is an active memory with basis model_inference, a short title, the dated letter in content, and the deduplicated canonical source IDs in references. Include sources only for verified HTTPS links using label and uri. Keep the source field within 500 UTF-16 units. Credit the actual writer in the letter and source attribution. The authenticated connection supplies the proposing harness identity.
5. Report successful admission as pending owner review with the proposal ID. Approval occurs in the owner's Living Memory inbox. It makes the record canonical under the owner-review actor, while the letter and proposal retain writer and proposer attribution. A correction approved on the original ID adds a revision. An authorized reader can retrieve the earlier revision with mother_get_record_history using the same id and prior revision.

If a submission result is uncertain, keep the exact request and operationId. Check mother_get_receipt with that ID first. Only retry the identical request under the same workspace and generation when the original receipt cannot be found and the owner still authorizes submission. If the read cannot confirm either state, report the unknown outcome and retain the pending request. A definite revision conflict requires a fresh read and a new owner-approved correction draft, with a new operationId. A missing proposal tool or insufficient grant leaves the draft unsaved.
